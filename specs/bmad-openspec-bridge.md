# bmad-openspec-bridge.md

> **Status**: v1.0.0. New in ai-playbook v0.7.0. Defines the canonical handoff between Phase 2 (BMAD discovery + design) and Phase 3 (OpenSpec implementation) of [runbook-bmad-openspec.md](runbook-bmad-openspec.md). Resolves the v0.6.x drift where BMAD skills ended with "invoke `bmad-help`" and `openspec-propose` had no contract for reading the slicing output — leaving a manual gap that broke at scale (e.g. proposing 11 changes for nexandro Module 2).

## 1. Purpose

The hybrid BMAD+OpenSpec workflow has a seam between phases:

- **Phase 2 ends** at Gate C — the human-led, agent-assisted slicing produces a list of change IDs each with scope, dependencies, and FR coverage.
- **Phase 3 starts** at `/opsx:propose <change-id>` — which scaffolds the change folder, the proposal, the design notes, and the tasks.

Before this spec, the seam was implicit. BMAD wrote slicing notes to `_bmad-output/planning-artifacts/slicing.md` (or wherever the agent felt like) and `/opsx:propose` had no idea where to look — the human was expected to retype scope notes into the propose prompt for every change. At 11+ changes per module, that is the drift surface.

This spec makes the seam explicit. There is one canonical slicing artefact, with one canonical location, one canonical schema, and `openspec-propose` reads it.

## 2. Path canon (settle the `docs/` vs `_bmad-output/` confusion)

Two trees coexist:

| Tree | Purpose | Stewardship |
|---|---|---|
| `docs/` | **Canonical durable artefacts.** PRD, ADRs, data model, project structure, `docs/ux/DESIGN.md` + per-journey docs, `docs/ux/components.md`, and (per this spec) `docs/openspec-slice.md`. These survive milestones and are reviewed at gates. | Human-edited (or BMAD/UX skills writing on the human's behalf). PR-reviewed. |
| `_bmad-output/planning-artifacts/` | **Workflow trail.** BMAD step-by-step audit per skill run. Records what each skill did, with timestamps, for retro/debug. | Auto-generated by BMAD skills. Not PR-reviewed; gitignore-able for some teams. |

**Rule**: anything that informs Gate B / Gate C / Gate D / Gate F approval lives in `docs/`. Anything else (workflow breadcrumbs, intermediate scratch) lives in `_bmad-output/`. When a BMAD skill produces both, it writes the canonical version to `docs/` and the trail to `_bmad-output/`.

## 3. The slicing artefact: `docs/openspec-slice.md`

Produced at the end of Phase 2 slicing (runbook §2.4). Approved at Gate C. Read by `openspec-propose` at the start of Phase 3.

### 3.1 Schema

```markdown
---
title: <Module name> — OpenSpec slicing
date: YYYY-MM-DD
approver: <who signed Gate C>
prereq_gates:
  - Gate A — <date>
  - Gate B — <date>
status: approved | proposed | superseded
runbook: .ai-playbook/specs/runbook-bmad-openspec.md §2.4
---

# <Module name> — OpenSpec slicing

<one-paragraph context: what was sliced + how many changes>

## Approved change list

| # | Change ID                  | Bounded context | FRs           | Journeys (if UI) | Components (if UI)        | Depends on |
|---|----------------------------|------------------|---------------|------------------|---------------------------|------------|
| 1 | `<module>-data-model`      | shared kernel   | (foundation) | —                | —                         | —          |
| 2 | `<module>-<feature>`       | <BC>             | FR<n-m>      | J<x>             | <Comp1>, <Comp2>          | #1         |
| ...                                                                                                                            |

## Scope notes

### 1. `<module>-data-model`
<one-paragraph: what's in scope, what's out, key entities/migrations>

### 2. `<module>-<feature>`
<one-paragraph each>
```

### 3.2 Field semantics

- **Change ID**: kebab-case, `<module>-<feature>` shape, ≤6 words, valid as a directory name. The kebab-case slug becomes the `openspec/changes/<id>/` folder. Conflicts across modules are forbidden — module prefix mandatory.
- **Bounded context**: the DDD context this change belongs to. `shared kernel` is allowed for foundational changes (data model, infra) that cross contexts.
- **FRs**: comma-separated list or range — `FR1-8` or `FR21, FR23, FR25`.
- **Journeys**: if the change has UI surface, the per-journey docs (`docs/ux/jN.md`) it consumes. `(infra)` if pure backend.
- **Components**: if UI, named components from `docs/ux/components.md`. Empty if backend.
- **Depends on**: change IDs that must land before this one. `—` if independent.

The scope notes (one paragraph per change) are what `openspec-propose` echoes into the scaffolded proposal as the initial framing. They MUST be copy-paste-quality prose (no `<TBD>` placeholders).

### 3.3 Authoring

The slicing artefact is human-led, agent-assisted (per runbook §2.4):

1. The agent (or a `Plan` subagent) drafts the slicing based on PRD + ADRs + UX docs.
2. The human reviews + edits + approves at Gate C.
3. The agent writes the approved version to `docs/openspec-slice.md`.

Re-slicing a module (e.g. mid-implementation a change splits in two) is a new file revision: `git mv docs/openspec-slice.md docs/_archive/openspec-slice-<old-date>.md` and write the new one. Never edit silently.

### 3.4 Multi-module repos

Projects with multiple modules in flight can have one slicing file per module: `docs/openspec-slice-module-1.md`, `docs/openspec-slice-module-2.md`. The default name `docs/openspec-slice.md` is reserved for single-module projects or the active module.

`openspec-propose` accepts `--slice-file <path>` to disambiguate; default is `docs/openspec-slice.md` falling back to the most recent `docs/openspec-slice-*.md` by mtime.

## 4. Phase 2 → Phase 3 handoff

The end of each Phase-2 BMAD skill points at slicing:

- `bmad-create-prd` step-final: "Approved at Gate A → next: Phase 2 design (Architecture + UX in parallel)."
- `bmad-create-architecture` step-final: "Architecture done → next: wait for UX (parallel) then Gate B."
- `bmad-create-ux-design` step-final: "UX track done → next: wait for Architecture (parallel) then Gate B."
- After Gate B: "Run slicing per runbook §2.4. Write `docs/openspec-slice.md`."
- After Gate C: "Begin Phase 3 — run `/opsx:propose <change-id>` per row in `docs/openspec-slice.md`."

`/opsx:propose` reads the slicing file at start. Workflow:

1. Parse `docs/openspec-slice.md` (default location; `--slice-file <path>` overrides).
2. Locate the table row for the requested `<change-id>`.
3. If not found: emit error "change-id not in slice list; either add it (re-slice + re-approve Gate C) or pass --no-slice for ad-hoc changes".
4. Use the row's scope note as the initial proposal framing.
5. Use the dependencies column to write the proposal's "Prerequisites" section.
6. Use the components column (if UI) to enrich the design.md with token + state references from `docs/ux/components.md`.
7. Use the FRs column to populate the proposal's "Capability coverage" section.

Result: `/opsx:propose <id>` is now a one-shot from human approval at Gate C to a fully-scaffolded proposal that already cites the right ADRs, FRs, and component contracts.

## 5. Batch mode

For modules with many changes, `openspec-propose` accepts `--batch` which iterates every row in the slicing file and scaffolds in dependency order.

```bash
# Single change
/opsx:propose m2-recipes-core

# All changes in dependency order (foundations first)
/opsx:propose --batch
```

Batch mode is idempotent — if a folder `openspec/changes/<id>/` already exists, that row is skipped (with a notice) so re-running after partial completion works.

The batch run produces one summary at the end (which scaffolded, which skipped, which failed) instead of N separate confirmations.

## 7. Migration notes

For projects on ai-playbook v0.6.x or earlier without `docs/openspec-slice.md`:

1. The next time slicing runs (next module's Phase 2 close), produce the file per §3.
2. Existing `_bmad-output/planning-artifacts/gate-c-approval-*.md` files (the v0.6.x convention) stay as historical records — they are workflow trail; the new canonical lives in `docs/`.
3. `openspec-propose` falls back gracefully: if no slice file exists, it asks the user for the scope inline (legacy v0.6.x behaviour) — opt-out via `--no-slice`. The behaviour change is opt-in for now; will become mandatory in v1.0.0.
