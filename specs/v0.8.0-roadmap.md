> **Status**: planning. Records design objectives + work items deferred from v0.7.0 to v0.8.0. This is not a commitment to ship every item; it is the working list when the v0.8.0 PR opens. Each item carries enough context that whoever picks it up can act without re-discovering the rationale.

## Why deferred

v0.7.0 was scoped as "alignment + bridges + audit incorporation": resolve the BMAD↔OpenSpec drift, lift two patterns from the taste-skill / superpowers audits as new specs, add a soft-warn lint for SKILL.md description quality, and ship the slicing artefact contract. ## Design objectives (substantial — each warrants its own ADR + design conversation)

### 1. KISS single-versioning source

**Motivation** (Master, 2026-04-28): *"yo creo que solo deberia versionarse el ai-playbook y no las cosas que tiene dentro, KISS"*.

Today the playbook ships two semver streams (ai-playbook + eligia-skills) and consumers pin each independently in `consumers.yaml` `skills_pins:` + `AGENTS.md` `skills_sources:`. Drift surfaces between AGENTS.md and the actual submodule, and across consumers.

**Proposed**:
- Collapse to one canonical semver stream — `ai-playbook`.
- Skills live at a pinned commit (or sub-tag) inside the playbook tree (or as submodules of the playbook itself, not of each consumer).
- Consumers pin only `ai-playbook@vX`. The skills pin is implicit — whatever the playbook tag references.
- One propagation workflow (`propagate-playbook-bump`) handles everything.

**Impact**:
- Reduces: AGENTS.md drift, cross-consumer pin inconsistency, two propagation routes.
- Trade-off: a consumer cannot independently pin `skills@v0.5` while staying on `playbook@v0.6`. We bet that case is rare (and if it arises, fork the playbook).

**Investigation tasks**:
- ADR proposal: collapse-to-single-versioning.
- Spec proposal: how do `consumers.yaml.skills_pins` migrate? Migration window?
- Open question: do source repos like `eligia-skills` keep their own semver for external use, while the playbook pins them at a known-good SHA internally?

### 2. Complete the bmad-create-ux-design v1→v2 migration

In v0.6.0 we rewrote `templates/new-project/.claude/skills/bmad-create-ux-design/workflow.md` to v2 (three-step order, palette decoupling, OKLCH-canonical, etc. — per `specs/ux-track.md` v2.0.0). The `steps/` files underneath were not migrated and still produce the v1 monolithic `ux-design-specification.md`.

**Why deferred from v0.7.0**: openTrattOS's M2 UX is already done, so this only affects future projects. Substantial work (15+ step files) — enough to warrant its own focused PR.

**Action**: rewrite each step under `bmad-create-ux-design/steps/` to produce the v2 artefact ladder (`docs/ux/inspiration.md` → `palette-options.html` → `variants/` → `DESIGN.md` → `jN.md` → `components.md`). Validate end-to-end on a fresh module.

### 3. Vendor / lift `systematic-debugging` from superpowers

The audit recommended `systematic-debugging/SKILL.md` from `obra/superpowers` (MIT) as a worker-side replacement for the `bmad-quick-dev` debug path during `/opsx:apply` Phase 3.2. Formalises a 4-phase root-cause sequence + the "3 failed fixes ⇒ question architecture" stop rule.

**Why deferred from v0.7.0**: touches the worker→QA contract; needs an ADR + a real test on Module 2 before generalising.

**Action**:
- Lift (don't vendor) the pattern into a new skill at `templates/new-project/.claude/skills/systematic-debugging/`.
- Cite source per `specs/output-completeness.md` provenance posture (no whole-file vendoring; cite repo + license at the top).
- Wire the "3 failed fixes" rule to emit `⛔ ARCHITECTURE QUESTIONED` per `verdict-contract.md` v1.1.0.

### 4. Two-stage review split (spec-compliance vs code-quality)

From the superpowers audit. Currently `bmad-code-review` conflates "did you implement the spec" with "is the code good". Splitting into two reviewers (sequential or parallel) lets compliant-but-ugly code get caught separately from incompliant code.

**Why deferred**: requires changes to `parallel-review.md` and the QA worker contract; not blocking.

**Action**: ADR on the split + revise `parallel-review.md` + revise `bmad-code-review` step structure.

### 5. Scan→Diagnose→Fix audit shape

From the taste-skill audit (`redesign-skill`). Three-phase audit format that reads tighter than free-form review prompts.

**Action**: adopt as the pattern for `bmad-code-review`, `bmad-review-adversarial-general`, and `bmad-review-edge-case-hunter`. Update each skill's `steps/` to use the format.

### 6. 3-dial parameterization for non-UX skills

From the taste-skill audit. The pattern (`DESIGN_VARIANCE` / `MOTION_INTENSITY` / `VISUAL_DENSITY`) generalises: a skill exposes 1–3 dials that conditionally tune its rules. Non-UX analogues: `RIGOR` / `VERBOSITY` / `RISK_TOLERANCE` for skills like `bmad-quick-dev` or `openspec-propose`.

**Action**: prototype on one skill (probably `bmad-quick-dev`), measure value, then generalise.
