# RFC 0001 — Skills distribution: copy-paste → semver-pinned submodule + per-LLM adapter copies

- Status: accepted
- Author: Arturo Ramírez
- Opened: 2026-04-26
- Decided: 2026-04-26
- Affects: schema (AGENTS.md frontmatter), dispatcher-chain, bootstrap, specs (skills-registry.md), templates (new-project), CHANGELOG

## Context

Today, every consumer project has a private copy of every skill it consumes:

- `nexandro/.claude/skills/` — ~52 BMAD + 4 OpenSpec skills (~3.5k LOC)
- `eligia-core/.claude/skills/` — 7 BMAD agents (subset of the above)
- `iguanatrader/.claude/skills/` — 2 BMAD skills (just-copied snapshot)
- `palafito-b2b/.claude/skills/` — empty
- `eligia-skills/` (root, pre-`backend/`) — 75+ custom skills (overlap with nexandro for non-BMAD ones)
- `Wizarck/skills-manager-personal` (frozen 2026-04-07) — predecessor of `eligia-skills`, identical content for shared skills, **no installer remaining** (CLI lived on a now-decommissioned PC)

Three concrete failure modes today:

1. **Drift.** A fix to `bmad-code-review` in nexandro does not propagate to eligia-core. Sessions in different consumers behave differently with no audit trail of "why."
2. **No reproducibility.** `git checkout <sha>` in any consumer does not restore the agent behaviour that was active when that commit landed: skills are floating local copies.
3. **No canary or rollback.** Updating a skill is per-repo manual `cp -r`. A regressing skill change ships everywhere or nowhere; there is no equivalent to the `inherits_from: <playbook>@v0.3.1` semver pin we already enforce for the playbook itself.

The HTTP registry at `eligia-skills.palafitofood.com` (FastAPI in `eligia-skills/backend/`) is **discovery-only** by design — it returns a catalog of `{name, description, scope, version, source, updated}` per `specs/skills-registry.md`, never the SKILL.md content. So distribution is not a registry concern.

The pre-T20 spec ("everything shared comes over the wire") was aspirational; what shipped is the discovery surface alone. We need a distribution mechanism with the same audit/versioning posture the playbook itself enjoys, **without** re-implementing a content-distribution registry.

## Proposal

Treat skills the same way the playbook is already treated by consumers: **semver-tagged source repos, pinned per consumer, materialised by a deterministic bootstrap step.**

### 1. Canonical layout (LLM-agnostic)

```
<source-repo>/
  skills/
    <skill-name>/
      SKILL.md              ← canonical, vendor-neutral
      [steps-c/, templates/, data/, ...]
```

Two source repos initially:

- **`ai-playbook/skills/`** — methodology skills shipped with the playbook (BMAD family, OpenSpec family, BMAD upstream-tracked).
- **`eligia-skills/skills/`** — Arturo's custom skills (e.g. `mcp-builder`, `qa-poc`, `kickoff`, `nuevo-lote`). Note: the FastAPI backend stays in `eligia-skills/backend/`; only the catalogued skills move under `skills/`.

The path is deliberately `skills/`, **not** `.claude/skills/`. Skills are a vendor-neutral artefact (a SKILL.md is just a Markdown contract); `.claude/` is one consumer. Other agent CLIs (Gemini, Antigravity) consume the same files via their own conventions.

### 2. Consumer-side materialisation (per-LLM adapter via copy)

Every consumer has:

```
<consumer>/
  skills/                   ← submodule sparse-checkout, source-of-truth
  .claude/skills/           ← gitignored, regenerated by bootstrap
  .gemini/skills/           ← gitignored, regenerated by bootstrap
  AGENTS.md
    frontmatter:
      inherits_from:
        - github.com/Wizarck/ai-playbook@v0.4.0
      skills_sources:
        - github.com/Wizarck/ai-playbook@v0.4.0     # methodology
        - github.com/Wizarck/eligia-skills@v0.2.0   # custom
```

**Materialisation algorithm** (idempotent; `bootstrap.py` extension):

1. Parse `skills_sources` from AGENTS.md frontmatter.
2. For each source, sparse-checkout `skills/` from the pinned tag into `<consumer>/skills-<repo-slug>/` (or merge under a single `skills/` if no name collisions; collisions error with `❓ CLARIFICATION NEEDED`).
3. **Copy** (not symlink) the merged `skills/` to `.claude/skills/` and `.gemini/skills/`.
4. Drift check: hash of `skills/` must equal hash of `.claude/skills/` and `.gemini/skills/`. Pre-commit hook enforces this.

Why **copy** instead of symlink/junction:

| | Symlinks/Junctions | Copy |
|---|---|---|
| Windows native (no admin/Dev Mode) | ❌ Requires `mklink /D` privileges or symlinks=on git config | ⭐ Trivial |
| Cross-shell consistency (Git Bash / PowerShell / WSL / VS Code) | ⚠️ Inconsistent resolution | ⭐ Identical |
| Debug "what skill is the agent reading?" | ❓ FS-dependent target resolution | ⭐ `cat .claude/skills/X/SKILL.md` |
| Storage overhead | ~0 KB | ~5–50 MB per consumer |
| Re-bootstrap cost | n/a | 1–2 s |

Storage is cheap; debug ergonomics and Windows-portability are not. The pre-commit drift check makes copy as audit-tight as a symlink.

### 3. Versioning + propagation

- Both source repos cut **independent semver tags**.
- `consumers.yaml` extended with `skills_pins`:

  ```yaml
  - repo: Wizarck/iguanatrader
    default_branch: main
    visibility: private
    status: active
    inherits_playbook: v0.4.0
    skills_pins:
      ai-playbook: v0.4.0
      eligia-skills: v0.2.0
  ```

- New workflow `propagate-skills-bump.yml` (sibling of existing `propagate-playbook-bump.yml`):
  - Triggers on tag push to `ai-playbook` or `eligia-skills`.
  - Opens a PR per consumer in `consumers.yaml` bumping the relevant `skills_pins.*`.
  - Idempotent (skips if pin already at target).

- New script `scripts/propagate_skills_bump.py` mirrors `propagate_bump.py` semantics.

### 4. Registry stays as discovery

`specs/skills-registry.md` is updated to clarify:

- HTTP registry is the **catalog surface**: it answers "what skills exist in scope X?", returns metadata only, NEVER content.
- Distribution is git submodule + sparse-checkout per RFC-0001.
- The registry's `source` field in each catalogue entry now explicitly points to a `skills/` path inside a source repo (e.g. `Wizarck/ai-playbook@v0.4.0:skills/bmad-create-prd/`), not a raw SKILL.md URL.
- Drift between catalog and source repo is detected by a new periodic CI step (`drift_check.py --scope skills-catalog`).

### 5. Bootstrap and templates

- `templates/new-project/.gitignore.tmpl` adds `.claude/skills/`, `.gemini/skills/` (skills/ stays tracked via submodule reference).
- `templates/new-project/AGENTS.md.tmpl` gains an `skills_sources` block defaulted to the playbook itself; consumers add eligia-skills opt-in.
- `scripts/bootstrap.py` runs the materialisation step at end-of-bootstrap and on every subsequent invocation. Existing consumers re-run it as part of the migration.
- Pre-commit hook `validate-skills-mirror.py` detects drift between `skills/` and the per-LLM mirrors.

### 6. Fallback / degraded mode

If a source repo is unreachable at materialisation time:

1. The consumer's existing `skills/` (last good submodule state) remains usable — `.claude/skills/` is regenerated from local content.
2. `bootstrap.py --skills-offline` skips the fetch, regenerates only from the present submodule. Errors clearly if `skills/` is empty.
3. The agent surfaces `DEGRADED_CONTEXT` (per `specs/degradation-modes.md`) when materialisation fails partially.

## KPIs (success criteria for the migration)

| KPI | Target | Measured by |
|---|---|---|
| Skill content duplication across consumers | 0 (each skill has 1 canonical home) | `find . -name SKILL.md -exec sha256sum {} \;` over all consumer working trees → unique hashes |
| Reproducibility | 100% — `git checkout <consumer-sha>` restores exact agent behaviour | Spot-check: `git checkout HEAD~10 && bootstrap.py && diff -r .claude/skills/X $(git stash; cat skills/X)` |
| Audit trail per skill change | Single PR per propagated bump per consumer | `gh search prs --label skills-bump` returns one PR per consumer per source-repo tag |
| Windows portability | Bootstrap completes from clean clone with no admin / Dev Mode toggles | Manual smoke test on Win11 Pro (Git Bash + native PowerShell) |
| Time from "fix in source repo" to "all consumers pinned to fix" | ≤ 24h elapsed (≤ 5 min CI + reviewer wall-clock) | Tag → propagation workflow → first PR open delta |
| Rollback | Revert PR in single consumer reverts skill behaviour in that consumer alone | Manual smoke test |

## Functional requirements

1. **FR-1**: A consumer can declare any number of `skills_sources` entries, each a `<owner>/<repo>@<tag>` ref.
2. **FR-2**: `bootstrap.py` materialises all declared sources idempotently into `<consumer>/skills/`, then regenerates `.claude/skills/` and `.gemini/skills/`.
3. **FR-3**: Skill name collisions across sources are detected at materialisation time and produce a `❓ CLARIFICATION NEEDED`-shaped error (per `specs/error-message-standard.md`); no silent last-wins.
4. **FR-4**: Pre-commit hook rejects the commit if `.claude/skills/` ≠ `skills/` (drift).
5. **FR-5**: `propagate-skills-bump.yml` opens consumer PRs on tag push of any source repo present in `consumers.yaml`.
6. **FR-6**: HTTP registry's catalog response includes a `pin_recommended: <semver>` hint per skill (the source repo's latest stable tag), so consumers can compare their pin to the upstream's recommendation.
7. **FR-7**: A new `runbooks/skills-version-bump.md` documents the maintainer's workflow: edit skill → tag source repo → review propagation PRs → merge.

## Non-functional requirements

- **NFR-1**: Bootstrap materialisation completes in ≤ 30 s for a consumer with 2 source repos and 100 total skills (cold submodule fetch on a 100 Mbps link).
- **NFR-2**: Idempotency: re-running `bootstrap.py` with no source-repo changes is a no-op (no file modifications, no git status changes).
- **NFR-3**: No symlinks / junctions on disk anywhere — copy-only model.
- **NFR-4**: `skills/` checked into consumer git via submodule reference; per-LLM mirrors gitignored.
- **NFR-5**: Sparse-checkout limits the consumer's local clone to `<source>/skills/*` only — never the whole source repo (exception: `eligia-skills/backend/` for the registry deployment, which is a separate concern).

## Consumer impact

The migration is **breaking but mechanical**: every consumer needs a single PR. No semantic changes to skills themselves.

### Per-consumer migration recipe

1. `git rm -r .claude/skills/` (and any other tracked skills locations).
2. Add submodule(s) per `skills_sources`: `git submodule add -b v0.4.0 <source-repo>.git skills-<source>` (with sparse-checkout pattern `skills/`).
3. Update AGENTS.md frontmatter: add `skills_sources` block.
4. Append `.claude/skills/`, `.gemini/skills/` to `.gitignore`.
5. Run `python .ai-playbook/scripts/bootstrap.py --refresh-skills` → regenerates per-LLM mirrors.
6. Smoke-test: `/<key-skill>` invokes correctly in Claude Code; `gemini --skill <key>` works in Gemini.
7. Pre-commit passes (`validate-skills-mirror.py` finds no drift).
8. Commit + PR; auto-propagate workflow takes over for future bumps.

### Repo-by-repo blast radius

| Repo | Files removed | Files added | Submodules added | Estimated effort |
|---|---|---|---|---|
| `nexandro` | ~600 (52 bmad + 4 openspec, ~10 files each) | 1 (.gitmodules update), 4 (AGENTS.md/spec rows) | 1 (`ai-playbook/skills/`) | 30 min |
| `eligia-core` | ~140 (7 bmad agents) | same | 1 | 30 min |
| `iguanatrader` | ~20 (2 bmad just copied) | same | 1 or 2 | 20 min |

| `ai-playbook` | n/a (source repo, populate `skills/` from nexandro canonical) | this RFC + new spec + new runbook + `propagate_skills_bump.py` + workflow | n/a | 2–3 h |

### Deprecations

- `Wizarck/skills-manager-personal` — **archive on GitHub** (Settings → Archive). Frozen since 2026-04-07; superseded by `eligia-skills`. No code rescued.
- The aspirational "registry distributes content" prose in older drafts of `specs/skills-registry.md` — replaced by the discovery-only contract clarified in §4 above.

## Alternatives considered

### A. Symlinks / junctions from each consumer to the central repo

The user's original instinct: one repo, every consumer points back via FS link.

Rejected because:

- **Windows symlinks require admin or Developer Mode** — the user runs Win11 Pro and the team will eventually too. Junctions work but need `mklink /J` per shell, are not git-tracked cleanly, and break under Git Bash's path-mangling.
- **Floating ref by default** — symlinks to HEAD propagate every push to every consumer instantly. Skills are prompts that change agent behaviour; a regression in a skill ships to live trading bots and PR reviewers alike. The friction of a propagation PR is a safety feature, not a cost.
- **Reproducibility lost** — `git checkout <sha>` of a consumer doesn't restore the symlink target's state at that time.
- **VPS-driven force-pull** (the next layer of the original idea) creates a control plane outside git, with non-idempotent timing risk on developer machines.

### B. Skills-as-content via the HTTP registry

Extend `eligia-skills/backend/` to serve SKILL.md content (not just metadata), client downloads on demand into a local cache.

Rejected because:

- Network dependency at agent startup (registry up = work; registry down = degraded).
- Cache invalidation correctness becomes a hard problem (HTTP ETags vs git SHAs).
- Auth scope creep — `scope=personal` content over HTTP needs robust bearer-token rotation.
- We already have a perfect content-distribution mechanism: **git**. Reinventing it inside FastAPI is rope to hang on.

### C. Single monorepo for all skills

Merge `ai-playbook/skills/`, `eligia-skills/skills/`, and any future skills repo into one.

Rejected because:

- Methodology (BMAD upstream-tracked, AGPL-style community) and personal/custom (Arturo's playbook) have different audit trails, visibility, and release cadences. Coupling them couples decisions that should remain independent.
- The two-repo split mirrors the existing public/private split (`nexandro` AGPL community vs. `palafito-b2b` enterprise). RFC-0001 just extends the same pattern to skills.

### D. NPM package per skill

Distribute each skill as `@wizarck/skill-bmad-create-prd@1.0.0` etc., consumer installs via `package.json`.

Rejected because:

- ~75 skills × per-skill semver = administration nightmare.
- Skills are not JS code; npm is the wrong package manager.
- Discoverability via `npm search` is worse than the existing HTTP registry catalog.

## Decision

**On acceptance**, this RFC ships as `ai-playbook v0.4.0` with the following companion artefacts (separate PRs for review hygiene, all bundled in the v0.4.0 release):

1. `specs/skills-distribution.md` — the formal contract this RFC sketches in prose.
2. `specs/skills-registry.md` — updated to clarify discovery-only scope.
3. `runbooks/skills-version-bump.md` — maintainer procedure.
4. `scripts/propagate_skills_bump.py` + tests.
5. `.github/workflows/propagate-skills-bump.yml`.
6. `templates/new-project/.gitignore.tmpl`, `AGENTS.md.tmpl` updates.
7. `scripts/bootstrap.py` extension + `validate-skills-mirror.py` pre-commit hook.
8. `consumers.yaml` schema bump (new `skills_pins` field).
9. `eligia-skills v0.2.0` cut in parallel with the structural move from root → `skills/`.
10. Per-consumer migration PRs, sequenced nexandro → eligia-core → iguanatrader → palafito-b2b.

Semver impact: **minor** for `ai-playbook` (new optional schema field, all consumers continue working pre-migration); **minor** for `eligia-skills` (path restructure, but the FastAPI catalog endpoint remains backwards-compatible for a deprecation window).

Roll-forward strategy: see `specs/rollout-strategy.md`. Roll-back strategy: revert the per-consumer PR; the pre-RFC-0001 copy-paste model still works as a fallback because consumers' `git rm -r .claude/skills/` step is the last in the migration recipe.

## Implementation notes

Recorded during Phase 2 (tooling) implementation, 2026-04-26. Captures decisions made when the prose RFC underspecified an edge case.

### Submodule path layout

Submodules land at `<consumer>/.skills-sources/<repo-slug>/` (a hidden directory) instead of `<consumer>/skills-<source>/` (the RFC §2 sketch). Rationale: the canonical `<consumer>/skills/` is the consumer-visible artefact; sources are derived state used only by the materialiser. Hiding them under `.skills-sources/` keeps `ls` output of the consumer root clean and matches the hidden-derived-state convention already used by `.ai-playbook/` (the playbook submodule itself).

The mirrors at `.claude/skills/` and `.gemini/skills/` are the consumer-facing copies; the canonical merged tree at `skills/` is the reproducibility anchor. Per RFC §2, the merged `skills/` is union-of-sources; `_skills_materialiser._merge_sources` wipes it on every run so partial-state hand-edits never accumulate. The submodule references inside `.gitmodules` ARE the audit trail; the merged dir is regenerable.

### Sparse-checkout in submodules on Windows

`git sparse-checkout` works the same way under Git Bash, native Windows git, and WSL on Windows 11 ≥ git 2.25 (released 2020). The materialiser uses `--no-cone` mode for the broadest compatibility (cone mode requires git ≥ 2.27 with newer pattern semantics). On older gits or when sparse-checkout configuration fails for any reason, the fallback is a full submodule checkout — heavier but functionally correct.

The `_enable_sparse_checkout` helper is best-effort by design: if `git sparse-checkout` isn't available or returns an error, the script keeps going. Tests don't exercise this path since the suite stubs `_add_submodule` entirely; the smoke test (manual, post-Phase-5) is the place where sparse-checkout coverage actually lands.

### Idempotency via wipe-and-recopy

Both the merged `<consumer>/skills/` and per-LLM mirrors are regenerated from scratch on every materialiser invocation. The script does not attempt incremental sync. Reasoning: skills are O(MB), copying is O(seconds), and any incremental algorithm would have to defend against drift introduced between runs (`shutil.copytree` after `shutil.rmtree` is the simplest correct primitive). NFR-1 (≤ 30 s for 100 skills cold) easily holds.

Pre-existing `<consumer>/skills/` content is wiped without confirmation. This is the contract — `skills/` is derived state. Hand-edits go upstream (to a source repo), not into the merged tree.

### AGENTS.md frontmatter editing in `propagate_skills_bump.py`

The propagation script does NOT round-trip the entire YAML frontmatter through `yaml.safe_load` + `yaml.dump`. Instead, it walks the lines between the `---` fences and surgically rewrites the matching `- <owner>/<repo>@<tag>` line via regex.

Rationale: `yaml.dump` would re-quote, re-order, and strip comments — anything currently in `AGENTS.md` would change cosmetically, producing review noise that buries the actual semantic delta. The line-level edit produces a one-line diff that reviewers can verify at a glance. The cost is that the rewriter only handles canonical list-item syntax (`  - <owner>/<repo>@<tag>`); flow style, anchors, and other YAML niceties would silently fail to match. That's acceptable for a project convention enforced by `templates/new-project/AGENTS.md.tmpl`.

### Pre-commit hook scope

`validate_skills_mirror.py` is a strict consumer-side hook. It is silently a no-op when:

- `<consumer>/skills/` does not exist (consumer not yet migrated).
- Neither `.claude/skills/` nor `.gemini/skills/` exists (consumer mid-migration, before first materialise).

This makes the hook safe to land **before** every consumer migrates — it can be added to the playbook's own `.pre-commit-config.yaml` and the template `.pre-commit-config.yaml.tmpl` immediately, and it will only start firing once a consumer actually completes the migration recipe.

### `--refresh-skills` short-circuit

`bootstrap.py --refresh-skills` calls `materialise_skills()` directly and exits. It never re-runs slug validation, template copy, doctor, discover, mcp/render, or any other Phase 1 bootstrap step. This is the canonical post-merge command for a consumer that just took a propagation PR: re-resolve `skills_sources`, regenerate the mirrors, done.

The flag is **not** an alternative to the post-discover materialiser step; both call into the same `materialise_skills()` so behaviour is identical. The flag is just the "skip everything else" knob.

### Where Phase 2 stops

Phase 2 ships tooling only:
- `scripts/_skills_materialiser.py` + bootstrap wiring
- `scripts/propagate_skills_bump.py` + `.github/workflows/propagate-skills-bump.yml`
- `scripts/validate_skills_mirror.py` + `.pre-commit-hooks.yaml` + dogfood entry in `.pre-commit-config.yaml`
- `consumers.yaml` schema docs for `skills_pins` (no existing consumer touched)

Phase 5 (per RFC §6 deprecations) is the per-consumer migration that actually populates `skills_pins`, edits AGENTS.md, and removes `.claude/skills/` from version control. Phase 5 is out of scope for this commit batch.
