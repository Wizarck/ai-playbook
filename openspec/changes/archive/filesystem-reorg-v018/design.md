# Design — filesystem-reorg-v018

## Architecture

The playbook moves from a mixed-purpose flat layout (specs/scripts/docs/runbooks at root) to a Diátaxis-inspired layout under `docs/` with paired enforcement bound by slug convention.

```
.ai-playbook/
├── docs/
│   ├── rules/            # .rule.md  (paired L2 doc per L1 hook)
│   ├── concepts/         # reference + explanation (no enforcement language)
│   ├── runbooks/         # Diátaxis how-to (multi-step procedures)
│   └── tutorials/        # Diátaxis tutorial (learning-oriented)
├── scripts/
│   ├── rules/            # .rule.py  (paired L1 hooks; slug = filename stem)
│   ├── mcp/              # subsystem (kept)
│   ├── tracing/          # subsystem (kept)
│   └── <tooling>.py      # validators, generators, dispatcher (unchanged)
├── schemas/              # top-level (industry convention)
├── specs/                # operational YAMLs ONLY (zombies-manifest, co-edit-pairs)
├── templates/
├── skills/
├── tests/
├── .github/workflows/
│   ├── <slug>.rule.yml   # L3 paired enforcement
│   └── <op>.yml          # operational (test, docs-deploy, propagate-bump)
├── AGENTS.md  (≤500 lines, D14)
├── README.md
├── VERSION
├── CHANGELOG.md
├── pyproject.toml
├── .pre-commit-config.yaml
└── .pre-commit-hooks.yaml
```

## Discriminator: rules vs concepts (D4 + D9)

A spec with **explicit enforcement language** (`paired_hardrule:` frontmatter, `MUST`/`MUST NOT` RFC 2119 vocabulary, normative cues like "blocked"/"required") → `docs/rules/<slug>.rule.md`.

A spec without paired_hardrule and without enforcement language (pure reference / explanation) → `docs/concepts/<slug>.md`.

**When ambiguous: default to concepts.** Slice 5 (content rewrite) resolves the residual ambiguities — promoting concepts to rules where enforcement is justified, demoting rules to concepts where the spec is descriptive-only.

Enforced at validation time via disjoint schemas: `schema-rule-v1.json` forbids fields that `schema-concept-v1.json` requires and vice versa (D9).

## Pairing convention (D3 — slug-based, 4 signals)

Slug regex: `^[a-z][a-z0-9-]{1,40}$`. Frontmatter `slug:` is authoritative; filename derives from slug.

For each rule, all 4 of these must agree:

1. **Filename slug**: `scripts/rules/<slug>.rule.py` ⇔ `docs/rules/<slug>.rule.md` ⇔ `tests/test_<slug>.py` ⇔ `.github/workflows/<slug>.rule.yml`
2. **Frontmatter `slug:`** in `docs/rules/<slug>.rule.md` matches the filename
3. **`paired_hardrule:`** field in frontmatter points to the existing `scripts/rules/<slug>.rule.py`
4. **AGENTS.md Rule Map entry** (auto-generated by `gen_indexes.py`)

`scripts/validate_pairing.py` enforces all 4. `scripts/validate_pairing_oracle.sh` is a parallel ~30-line shell tripwire re-implementing the slug-existence check (D12 defense-in-depth).

## Workflow aggregation (D10/D14 stress-test mitigation)

To avoid CI burst on 50 rules (1 workflow per rule), 4.C aggregates rule-related workflows into ≤5 grouped workflows that fan-in:

1. `validate-pairing.rule.yml` — runs `validate_pairing.py`
2. `check-doc-language.rule.yml` — runs `check_doc_language.py docs/`
3. `check-link-integrity.rule.yml` — runs `check_link_integrity.py docs/`
4. `check-agents-md-size.rule.yml` — runs `check_agents_md_size.py`
5. `check-rule-schemas.rule.yml` — validates all `docs/rules/*.rule.md` against `schemas/schema-rule-v1.json` and all `docs/concepts/*.md` against `schemas/schema-concept-v1.json`

## Hook dispatcher design (D10 — ≤50ms SLA)

Single Python process loads all rule definitions ONCE per session (in-memory). `triggers:` frontmatter declares which tool calls the rule cares about (`Bash` / `Edit` / `Write` / `Read` / etc.). Dispatcher routes incoming PreToolUse/PostToolUse events only to matching rules, eliminating cold-start cost per call. Target: p50 ≤50ms total hook overhead per tool call on Windows.

Benchmark mode: `python scripts/hook_dispatcher.py --benchmark` runs 1000 simulated events through the dispatcher and reports p50/p95/p99.

## Migration script (4.B — one-shot)

`scripts/migrate_paths_v0.18.py` walks `.md`, `.py`, `.yaml`, `.json` files and applies a static rename mapping:

- Markdown links: `](old/path)` → `](new/path)`
- Python imports: `from scripts.foo` → `from scripts.rules.foo` (only for paired scripts)
- YAML path strings: `specs/foo.md` → `docs/rules/foo.rule.md` or `docs/concepts/foo.md`
- JSON refs: same as YAML

After verification (`grep` for known-bad paths returns empty), the script is **deleted in the same PR**. CHANGELOG entry is the historical record per plan.
