# design — `single-source-skills-reset`

> Architecture for slice 3 of the ai-playbook reset (v0.17.0 BREAKING).
> Companion to [proposal.md](proposal.md) and [tasks.md](tasks.md).

## 1 New materialiser flow

```
INPUT: <playbook-root>/skills/  (the single source of truth)
OUTPUT: <consumer>/skills/, <consumer>/.claude/skills/, <consumer>/.gemini/skills/

1. Resolve <consumer>/. ai-playbook/skills/ (the playbook submodule path).
   If missing -> exit 1 with canonical error ("run git submodule update --init").
2. For each of (skills/, .claude/skills/, .gemini/skills/):
   a. Compute sha256 fingerprint over (relpath, file-bytes) pairs of source.
   b. Compute fingerprint over the existing target (if any).
   c. If equal -> no-op for this target (idempotency).
   d. Else -> shutil.rmtree(target) (orphan removal) + shutil.copytree(source, target).
3. Exit 0 on success; 1 on any FS write failure; 2 on missing source.
```

No AGENTS.md frontmatter parsing. No git submodule add. No `.skills-sources/`
directory. No tag pinning. No `validate-skills-mirror` round-trip check (the
hash-equality check inside the materialiser obsoletes it).

### 1.1 Source path resolution

The materialiser is run from the consumer root. It resolves the source via:

```
source = consumer_root / ".ai-playbook" / "skills"
```

The `--source` CLI flag overrides for test fixtures and edge cases (e.g. local
development checkout outside a submodule).

### 1.2 Why three mirrors instead of two

Plan v9 §"Final file structure" calls for three mirror destinations:

- `<consumer>/skills/` — canonical user-visible mirror (still tracked? see §1.3).
- `<consumer>/.claude/skills/` — Claude Code reads from here.
- `<consumer>/.gemini/skills/` — Gemini CLI reads from here.

Geeplo's `sync_skills_local.py` already implements this fan-out. The upstream
materialiser inherits the pattern verbatim.

### 1.3 Tracked vs gitignored

All three destinations are **gitignored at the consumer side**. Adoption
checklist (slice 4 onward) appends to consumer `.gitignore`:

```
# Single-source skills mirrors (regenerated by scripts/sync_skills_local.py or
# .ai-playbook/scripts/materialise_skills.py on post-checkout/post-merge).
/skills/
/.claude/skills/
/.gemini/skills/
```

This deviates from the legacy RFC-0001 model where `<consumer>/skills/` was
tracked (via submodule references). The new pattern matches geeplo: all three
are derived state, regeneratable in seconds, and the source of truth is the
`.ai-playbook/` submodule pin.

## 2 Mirror destinations

| Destination | Read by | Tracked? | Regeneration trigger |
|---|---|---|---|
| `<consumer>/skills/` | Other tools, generic | No (gitignored) | post-checkout, post-merge, manual |
| `<consumer>/.claude/skills/` | Claude Code | No (gitignored) | post-checkout, post-merge, manual |
| `<consumer>/.gemini/skills/` | Gemini CLI / Antigravity | No (gitignored) | post-checkout, post-merge, manual |

All three are byte-identical copies of `.ai-playbook/skills/`. The materialiser
treats them as fungible — same content, different addresses.

## 3 Per-LLM start wrappers

Claude Code already has a session-start hook (configured via `.claude/settings.json`
PreToolUse / SessionStart). Gemini CLI does not have an equivalent built-in,
so the playbook ships an explicit wrapper script:

- **`scripts/gemini_start.py`** — wraps the `gemini` binary. Before exec'ing
  the CLI, it runs the playbook's context-injection step (`inject_context.py`)
  so Gemini sessions start with the same memory the Claude session would.
  Imported from geeplo's working copy (file already battle-tested locally).
  Upstream adaptation:
  - Bank-id derived from cwd's project (per projects registry) instead of hard-coded `geeplo`.
  - Secrets-env handling becomes optional (geeplo uses sops; not every consumer does).
  - Cross-platform identical to geeplo (POSIX `os.execvp`, Windows `subprocess.run`).

## 4 Zombies-manifest v2 entries

Eight new entries deprecate the multi-source artefacts. All cite the v0.17.0
removal milestone as `removed_in`. Each has explicit `source_pin` referencing
the pre-this-slice version (v0.15.0).

| id | tier | action | summary |
|---|---|---|---|
| `propagate-skills-bump-script` | 3 | report | `scripts/propagate_skills_bump.py` removed upstream; consumer wiring stale |
| `validate-skills-mirror-script` | 3 | report | `scripts/validate_skills_mirror.py` removed upstream; consumer wiring stale |
| `propagate-skills-bump-workflow` | 3 | report | `.github/workflows/propagate-skills-bump.yml` removed upstream |
| `rfcs-folder-removed` | 3 | report | `rfcs/` deleted upstream; consumer references to RFC-0001 stale |
| `skills-sources-submodule-v2` | 1 | delete | tightens existing `skills-sources-submodule` entry — now safe-delete unconditionally when single-source is adopted |
| `skills-sources-frontmatter` | 3 | report | expands existing `skills-sources-frontmatter-simplify` to flag ANY `skills_sources:` block (was: only single-entry) |
| `skills-pins-consumers-yaml` | 3 | report | `consumers.yaml.<name>.skills_pins:` keys are stale (no propagator reads them anymore) |
| `validate-skills-mirror-precommit-hook` | 3 | report | `.pre-commit-config.yaml` entries invoking `validate_skills_mirror` are stale |

Per `specs/cleanup-zombies.md` Tier 3 semantics: these are advisory-only.
Consumer never auto-mutates `consumers.yaml` or hand-authored hook configs.

Two additions adjust existing entries (no schema break — same entry id, refined
`reason` / `evidence`):

- `skills-sources-submodule` (Tier 1) — clarify that `removed_in: v0.17.0` (was: `deprecation_only`).
- `pre-commit-deprecated-hooks` (Tier 3) — extend to list the new removal date and reference v0.17.0 CHANGELOG entry.

### 4.1 Why Tier 3 for most entries

Multi-source artefacts in consumer trees are almost always paired with hand-
authored CI / `.pre-commit-config.yaml` / `consumers.yaml` lines. Auto-deleting
those would silently break a consumer that legitimately consumed multi-source.
Tier 3 keeps the surface visible in `zombie-report.md` so the consumer-merge
PR review surfaces the cleanup work explicitly.

The single Tier 1 entry (`skills-sources-submodule-v2`) targets a strict
orphan: the `.skills-sources/<repo>/` directory after `.gitmodules` has been
deregistered (same safety check as the existing v1 entry — `check_gitmodules_first`).

## 5 Backwards compatibility

RFC-0001 was accepted 2026-04-26; six weeks of life in upstream. The sole
consumer (Arturo's 5 sister repos) used it minimally — `consumers.yaml`
populated `skills_pins` for 4 active consumers, but only **geeplo** actually
ran the multi-source materialiser, and geeplo has already migrated away (PR
#125, 2026-05-18). The other 4 (nexandro, eligia-core, palafito-b2b,
iguanatrader) have `skills_pins` entries but never ran the materialiser in
production — their `<consumer>/skills/` trees are still snapshot copies from
the v0.3.x copy-paste era.

**No formal migration path** because there is nothing live to migrate. The
consumers either:

1. Already deviated (geeplo) — single-source pattern matches; no action.
2. Never ran the materialiser — `skills_pins` and `skills_sources:` are dead
   text. Slice 3.5 / 4 root-cleanup audit handles their removal.

The migration table in CHANGELOG.md documents the mechanical fixes any future
consumer needs, even though no current consumer requires them.
